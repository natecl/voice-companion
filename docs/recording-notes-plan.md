# Transcript-derived notes — delivery plan

Founder approved implementation September 26, 2026. Notes and summary are one feature: a useful, source-grounded note beside the original transcript. Build after-recording notes first, then separately evaluate notes-based retrieval as a possible memory simplification. Existing memory and recording-deletion behavior remain unchanged until a verified replacement and explicit contract decision.

## Checkpoints

1. **Contract and storage:** title, sourced overview and flexible sourced sections; revision-bound pending/generating/ready/failed/outdated states; idempotency, interruption, empty/oversized input, stale completion and deletion guards. No provider or app exposure in this checkpoint.
2. **Generation:** bounded Luna adapter and structured output; source-only prompt, no history/memory; no forced business template. Preserve uncertainty, corrections and speaker ambiguity. Verify five short representative saved/synthetic transcripts (conversation, lecture, appointment, reflection, correction), including actual provider output inspection. No automatic paid retries.
3. **Integration:** enqueue after terminal evidence synchronization, independent of capture/chat; expose state and saved notes to native recording view; Notes / Transcript navigation, generated title and passage links. Failed generation leaves transcript usable; explicit retry remains admission/budget-controlled. No automatic historical backfill.
4. **Physical acceptance:** after readiness and rollout approval, one short iPhone recording → notes → transcript/reference navigation → close/reopen. Inspect usage and server state. Focused shared-view Mac verification. Prior fixtures cover failures without repeating STT.

Each checkpoint is independently reviewed, tested and merged through a focused PR. Live QA, rollout and device readiness remain distinct gates. No note editor, templates, live notes, voice replies, proactive participation, or memory redesign in this slice. Generated notes are derived views, never independent evidence for learning.

## Checkpoint 1 — verified foundation

`Backend/recording_notes.py` stores notes in the same transactional database as their source. Schema 17 adds one table without backfilling existing recordings. Source revisions clear the old payload and mark outdated; recording deletion removes notes even when learned-memory retention is enabled. Atomic completion checks revision, generation version, attempt and state. A late failed or successful attempt cannot overwrite a retry. Startup interruption recovery marks failed and does not automatically retry. These methods are not yet wired into hosted scheduling or a network endpoint.

A note has a title (120 characters), a sourced overview and up to six sections/36 bullets. Every overview/bullet references existing passage IDs; sections are flexible rather than mandatory meeting categories. Validation proves structure and reference existence, not factual entailment or useful model quality. Bounds: 48,000 UTF-8 input bytes and 20,000 output bytes. Oversized input fails explicitly, never truncates. Empty transcripts are ineligible. Terminal incomplete recordings can produce notes with a server-derived incomplete flag; personal-text inputs are excluded. The caller must enqueue only terminal recording uploads, matching the existing native outbox boundary.

Verification uses real SQLite storage, synthetic transcript and injected note data, with no model calls. Twelve new checks cover persistence/reopen, duplicate requests, revisions, deletion before/after completion, retry races, interrupted jobs, incomplete/empty/oversized sources, owner isolation, malformed output and schema-16 migration. All 92 targeted checks passed, including existing memory/retention/chat and schema-migration tests, run because the database/source invalidation boundary changed. Initial fixture failures exposed schema expectations and repeat migration setup; the final migration follows the existing idempotent schema pattern and updated tests assert version 17. Failed logs are retained in ignored work storage.

Behavior receipt `work/notes-foundation/behavior.json`: reopened notes are ready with the original passage reference, source revision makes the payload unavailable/outdated, and deletion leaves zero notes rows. This proves storage behavior only. Generation, native UI and hosted enablement remain pending. No paid run, production migration, existing note generation or app behavior changed.

Rollback/deployment: the previous binary rejects schema 17. Deploy only with explicit approval and a consistent backup; use compatible rollback or forward-fix rather than restoring old content/usage. No live service was migrated for this checkpoint.

## Checkpoint 2 — generation quality

`notes_generation.py` builds a transcript-only structured-output request for GPT-6 Luna (no reasoning, default service tier, no tools, no storage, 3000 output-token cap), then validates and saves through the real revision/attempt-bound storage contract. A caller supplies provider and budget adapters. Provider failure, malformed output, interruption and budget rejection never trigger automatic retry. No hosted scheduling, network endpoint or native UI is enabled by this checkpoint.

Official API contract checked September 26: [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs). Schema adherence does not prove factual accuracy; app bounds and passage checks remain mandatory, with semantic review of actual notes.

Six live calls used the explicitly approved isolated $0.15 allowance (`recording-notes-20260926-015`), at $0.025 reserved per call. All completed; no retries. Five original synthetic cases covered a meeting, lecture, appointment, reflection, and corrected plan containing a quoted prompt injection. The initial reflection fixture incorrectly alternated labels; its output reflected that metadata. We retained it, corrected the input to a single speaker, and used the sixth call. Final notes preserve appointment uncertainty and conditional instructions, tentative reflection, explicit assignee only when stated, and the corrected final venue/day. The injected instruction was ignored. Some overview/bullet repetition remains an editorial limitation; speaker labels remain best-effort evidence.

Saved requests/responses: `Backend/fixtures/recording-notes/`. Exact-hash replay runs all five final cases through the real generator and SQLite, reopens ready notes, and verifies a second generation request makes no call. Four generator failure/contract checks supplement the 12 storage checks and recorded acceptance; the unittest invocation reports 29 because imported/inherited foundation tests are also discovered. Synthetic source material only, no secrets. Commands: `PYTHONPATH=Backend python3 -m unittest Backend/test_notes_generation.py -q`; `PYTHONPATH=Backend python3 Backend/evaluate_recording_notes.py <new-directory> --replay Backend/fixtures/recording-notes/calls.json`.

The allowance is exhausted by conservative reservations, not measured invoice cost. Funding is marked as an allocation rather than a microphone attempt. No deployed code/schema, app configuration, or permanent limits changed. Integration can use these cached outputs; further live notes require another explicit allowance.

## Checkpoint 3 — service and native integration

New terminal recording synchronization now inserts the notes job in the **same source transaction**, independently of memory learning. An unchanged/replayed upload cannot schedule another job or backfill an older recording. One background worker claims durable pending notes, defers starting a call while capture is active, and reserves its attempt before inference. Failed/uncertain attempts are not retried automatically; explicit Retry notes can enqueue a new bounded attempt. Startup marks interrupted generation failed. Credentials must remain enrolled to select background work. An already-running provider request is not preempted when another recording begins.

`/notes` authenticates ownership and checks the requested source revision. Reads never generate. Empty and oversized sources explain why notes cannot be made; retry cannot bypass those bounds. Deletion removes notes even under retained-memory mode. The existing memory harness and retained-claim behavior are unchanged. `/health/notes` exposes only worker state, failure code and completion count.

The native recording view offers Notes and Transcript, while active capture continues to show the live transcript. Notes contain a generated title, sourced overview and optional sections. Passage links open a highlighted passage in the transcript view using the synchronized revision. Library titles use read-only lazy loads, with a generic fallback offline. Reads poll at most ten times while generation is pending; switching away/reopening does not initiate inference. Cancellation closes the native socket. Notes live in server storage in this slice; unlike local transcripts, reopening notes requires a connection. No note editor, live summary, historical backfill or notes-based memory rewrite is included.

Runtime is **disabled by default**, using `VOICE_ENABLE_RECORDING_NOTES=1` only after separate rollout approval. Enablement requires an independently provisioned `notes-budget.sqlite`, an exact globally funded allocation marker, explicit call/count caps and the existing provider credential. Startup cannot grant its own allowance. The generation QA ledger is exhausted and cannot act as this new runtime budget. A reservation is retained after provider failure or uncertainty; recorded usage never silently refunds it.

Local verification evidence is in ignored `work/notes-integration/`: actual authenticated WebSocket source sync → queued job → synthetic provider → saved notes → reopened notes → deletion, plus failed generation/explicit retry, stale revision, owner isolation, revoked credential, no backfill and budget exhaustion. The storage/generator/memory group passed 60 discovered tests; the initial runtime group passed 12, and later affected contract checks passed after worker/health changes. These counts overlap, not independent totals. Mac build and the existing companion/capture UI flow pass. Native notes UI QA uses actual app, actual local service and SQLite with **synthetic capture and notes**, not new provider evidence. Initial UI failures were test-driver issues (offscreen Mac button, iOS static-text value versus label, nested alert button query, and reused fixture enrollment containing earlier test recordings); the evidence is retained rather than discarded. Physical phone and hosted provider integration remain checkpoint 4.

## Checkpoint 4 — proposed rollout gate

No notes deployment, live schema migration, new production budget or physical-device install occurred in checkpoints 1–3. After explicit approval: take a consistent backup, provision a separate bounded notes allowance from remaining global headroom, deploy schema-compatible code on the existing Render tier, enable notes, then verify authenticated readiness and zero unintended backfill. Preserve all previous charges and data. Disable the notes flag to stop new notes work; the pre-schema-17 binary cannot simply be put back over the migrated database.

Prepare the matching iPhone app before requesting readiness. Once the founder is ready, use one short recording with a clear fact and tentative plan, stop, inspect the generated notes and source passage, relaunch and reopen. Reuse this recording for UI checks; another model call requires a specific unresolved question and remaining allowance. The final hosted and physical-device result must be recorded before declaring the notes slice delivered.


Reproducible simulator command: `SIMULATOR_ID=<booted-simulator> VOICE_TEST_PYTHON=<python-with-websockets> scripts/qa-recording-notes-phone.sh`. It provisions a fresh synthetic owner each run, preserves evidence under `work/notes-phone-*`, and stops its local server afterward. Reusing an enrollment intentionally preserves sessions across relaunches, so it is inappropriate for independent test runs that assert an empty library after deletion.


Final local native receipts: Mac `work/notes-integration/native-fixed.xcresult` passes both the new notes flow and the existing companion/capture flow; iPhone 17 Pro simulator (iOS 26.5) `work/notes-phone-YtpbQv/native.xcresult` passes notes → supporting transcript → terminate/relaunch → same saved notes → deletion. The final simulator build includes source-revision change clearing and outdated-state handling. Screenshots from both platforms were inspected. This is not physical-iPhone or microphone evidence. No additional paid calls occurred during integration.
