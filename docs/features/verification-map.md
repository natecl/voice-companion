Each manifest names the expected evidence paths, acceptance and checks. The catalog lists implementation/test files for worker navigation. The orchestrator supplies the final feature packet before work, checks imported receipts and explicitly accepts the result. The generic runner alone cannot determine if a generated note is faithful or a rendered page is correct.

Adding/changing a feature: update its catalog entry, manifest, relevant tests and evidence scope together. Do not grant a feature pass by weakening a requirement or substituting replay for fresh model behavior. Use `--list` to discover feature IDs. No command triggers a paid API, microphone, device interaction or release automatically.

## Identity-provider evidence receipts

Account enrollment, native refresh/deletion recovery and revoked-provider/expired-session/network-failure checks use `live_identity_provider`, separately for Google and Apple. A receipt must match the manifest's `provider` (`google` or `apple`), record a positive integer `provider_calls`, and include nonempty `configuration` and `pipeline_layer` strings plus the ordinary `commit`, `kind`, `result`, `procedure`, `observed` and `artifacts` fields. Fixture identities or backend-only rotation cannot satisfy a native real-provider claim. These fields distinguish identity authorization from paid model QA; they require no model field and the verifier does not execute provider calls.

Receipt validation establishes evidence structure, not the truth of every claim or whole-feature acceptance. Primary must inspect the actual native/provider boundary, negative cases and scope. Physical deletion, independent-person isolation and operational backup/restore evidence remain distinct gates; existing successful simulator recovery does not satisfy them.
